# fde — commit/PR convention + CI-gate awareness for UIF

UIF ties every commit/PR to a Jira issue via branch/commit naming (**Smart Commits — rely on this**). Phase 2 (`jira-transition.yml`) is a future safety net when Atlassian admin resolves runner **401** (IP allowlist); until then a forgotten smart-commit token stalls traceability. This skill keeps the Smart Commit convention correct and explains *why* a gate failed, without ever committing/pushing on its own initiative.

## The convention (from `capabilities/delivery/jira-github-integration.md`)

- Branch and PR names carry the issue key: `<type>/UIFPE-<n>-<short-desc>`. The PR title must also *describe* the change, and the body must carry `## Summary` and `## Verification` sections — enforced by `.github/workflows/pull-request.yml`.
- Every commit that should move the issue forward needs **both** smart-commit commands: `UIFPE-<n> #comment <what changed> #<transition>` — `#comment` posts the text as a visible Jira comment (plain trailing text is NOT posted as a comment on its own), `#<transition>` is the target status name with spaces replaced by hyphens (e.g. `#code-review`, `#ready-for-qa`).
- The `#comment` text must **describe** the change (enforced floor: 20 characters, 4 words). When you draft a commit message for the engineer, write the `#comment` line as a one-line summary of the staged diff a PM could read — this is the part of your output that ends up on the Jira issue, and it is the only part most readers will see.
- The commit's **author email must be the engineer's own Jira-account address**. Jira runs each smart-commit action as the author, matched literally, and discards the command silently on no match — a `+alias` suffix matches nothing. This is enforced: `.github/workflows/commit-identity.yml` fails the PR if any non-merge commit has a plus-addressed or non-`@pearson.com` author.
- Lifecycle: first commit on the branch → In Progress. PR opened (non-draft) → Code Review (the "ready for PR review" signal). PR merged → Ready for QA (the "ready for testing" hand-off). Each hand-off should be backed by a Jira Automation rule that notifies the reviewer/QE Lead — see "Notifying QE and reviewers" in `jira-github-integration.md`.

## Workflow

1. **Check the branch name** carries a `UIFPE-<n>` key. If the user hasn't created the Jira issue yet, point them at the `pm` skill first — commits without a trace defeat the model.
2. **Check `git config core.hooksPath` is `.githooks` before the first commit of a session.** If it isn't set, the local commit-msg/pre-commit/pre-push hooks are inert and a bad commit only surfaces as a red PR. Tell the engineer to run `git config core.hooksPath .githooks` — it's a per-clone setting, not something the repo can turn on for them.
3. **Check `git config user.email` before the first commit of a session.** A shared or previously-configured machine may carry a colleague's address, in which case the commit lands under their name and posts the Jira comment as them. If it isn't the engineer's own Jira-account email, pass theirs on the commit (`git -c user.name=... -c user.email=... commit`) rather than committing and rewriting afterwards. Changing the machine's global config is the engineer's call, not yours — offer it, don't do it. Never use an agent alias or service address; credit the agent in a `Co-Authored-By:` trailer.
4. **Follow the Git Safety Protocol** (this is not optional, it's the baseline behavior for this whole environment): stage specific files by name, draft a commit message describing *why*, and only run `git commit`/`git push` when the user has explicitly asked for that specific action in this turn. Never chain "commit and push" onto an unrelated request.
5. **Before opening a PR**, know which of the two path-filtered workflows will fire:
   - `domain-ci.yml` runs only if the change touches `domains/**`. A `capabilities/`-only change triggers **zero** CI runs — this is expected, not a bug.
   - If `domains/<x>/**` is touched, the matrix job for `<x>` runs: structural DoD gate (`DOMAIN-CHECKLIST.md`, `src/schemas/`, `src/Dockerfile`, `qe/` must exist) → Entra ID + Keeper gate (only fires if `src/api/openapi.yaml` or `infrastructure/helm/templates/*.yaml` actually exist) → build/test/scan placeholder.
6. **Pre-PR conformance check.** Before drafting the PR, verify the change conforms to the capability standard(s) it touches — not just that CI will pass, but that a reviewer won't bounce it: schema registered in `src/schemas/` before the code that depends on it (Schema Registry First), folder/namespace placement matches the domain shape (`src/api/`, `src/events/`, etc. — see "Inside a domain" in the root README), and naming follows the relevant `capabilities/<capability>/guidelines.md` naming section (e.g. API resource nouns, event `<domain>.<resource>.<verb>`). This is a pre-PR checkpoint, not a live-typing check — skills only run when invoked.
7. **Draft the PR title and body to clear the PR gate.** `pull-request.yml` fails the PR unless the **title** carries `UIFPE-<n>` *and* names what it delivers (`UIFPE-39 · Product Data API` — a filler-only title like `updates` or `minor fixes` is rejected), and the **body** has a `## Summary` section (what changed and why, ≥40 chars / 8 words of prose) and a `## Verification` section (≥20 chars / 4 words — the command and its result, the CI job, the environment; an unticked checklist is not evidence). `.github/PULL_REQUEST_TEMPLATE.md` supplies the headings, and its HTML-comment guidance is stripped before measuring, so an untouched template fails like an empty body. Verify your draft with `.githooks/lint-pr.sh --title "…" --body-file <file>` before `gh pr create`, and show it to the user first. Write the summary so a PM can read it — for most readers it is the only description of the change they will ever see.
8. **If a CI gate fails**, read the failure message literally before proposing a fix:
   - Commit-identity gate (`commit-identity.yml`, runs on **every** PR regardless of paths) → a commit's author email is plus-addressed or not `@pearson.com`. The fix is to correct `user.email` and rebase with `--exec 'git commit --amend --no-edit --reset-author'`, not to seek an exception: this gate has no allowlist by design, because the failure it prevents is silent.
   - Smart-commit gate (`smart-commit.yml`, also every PR) → a commit has no `UIFPE-<n>` key, no `#comment <text>`, or a comment under 20 characters / 4 words. Fix by rewording with `git rebase -i <base>`. A `#<transition>` token is not required per commit; an unrecognised token is a warning, not a failure.
   - Pull-request gate (`pull-request.yml`, also every PR) → the title or body is not reviewable (see step 7). This is the only gate whose fix needs **no new commit**: edit the title/body on the PR and the check reruns. A keyless *branch* name is a warning, not a failure — renaming a branch would mean closing and reopening the PR.
   - Structural gate → a required file/folder is missing from the domain scaffold.
   - Entra ID gate → `src/api/openapi.yaml` doesn't declare `login.microsoftonline.com` as the OIDC identity provider.
   - Keeper gate → an `ExternalSecret` template doesn't reference `keeper-secrets-manager`, or references a disallowed store (AWS Secrets Manager / HashiCorp Vault / Azure Key Vault).
9. **Picking up a Bug filed from a CI failure.** `qe` drafts (never auto-files) Bugs from failing CI runs. Once one exists in Jira, it's picked up the same way as any other issue: branch `bug/UIFPE-<n>-<short-desc>`, same Smart Commit convention, same lifecycle. This skill doesn't file the Bug — see `qe` for that — it just means a CI-raised Bug isn't a special case once it's in Jira.

## What this skill does NOT do (stays with the FDE)

- **Design, security posture, and architecture decisions** — those come from `architect`, not here.
- **Deciding whether a PR is ready to merge** — the skill can summarize gate results; the merge/approve decision is always human.
- **Committing or pushing without being asked** — see step 4. This is the one rule this skill will never bend.
