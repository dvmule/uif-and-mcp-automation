# Gold Schema: Product v1

Master schema for the Product entity in the Gold layer (`gold_product.product`).
`master.json` is the source of truth the pipeline consumes — the transform
validates every produced row against it, and attribute lifecycle (ADR-3 D12)
auto-DDLs new columns straight from it. Nothing about the Gold table shape is
authored anywhere else.

## Files

- `master.json` — JSON Schema Draft-07. Each property is tagged with
  `x-channels` declaring tier membership (`event` ⊂ `message` ⊂ `api`).
- This README.

## Current shape

60 top-level attributes (55 + `categories` 2026-08-31 + `courseDurationQuantity`,
`courseDurationUnitCode`, `enablingTechnology`, `url` 2026-09-07 — UIFPE-270).
**PK:** `(inventoryItemId, organizationId)` — 1 row
per (EBS inventory item, organization). Both PK columns are internal
(`x-channels: []`); every consumer-facing attribute is tagged for at least
one tier. Property names are camelCase (`inventoryItemId`, `lineOfBusiness`) —
the logical name every contract carries; the physical Gold column is its
snake_case rendering (`inventory_item_id`), generated by the runtime per the
Schema Standards N8 (UIFPE-437, 2026-09-11). Nothing hand-writes a physical name.

One consequence to know: `_channel_hashes` serialise a nested column whole, so
struct member names are part of the hash. The 2026-09-12 rename to snake_case
moved every hash on a row with nested data — a one-time move, contained by a
silent refresh (no change-log rows, no timestamp bump). The basis is stable
now; a future rename of a nested member would move hashes the same way.

Most attributes are flat scalars sourced from `MTL_SYSTEM_ITEMS_B` /
`EGO_MTL_SY_ITEMS_EXT_B` (see the mapping manifest's `canonical_lineage` for
the PDH table/column/attribute-group behind each one — many are conditional
on `ITEM_CATALOG_GROUP_ID = 10002`, i.e. Digital Catalog items, sourcing from
a different attribute group than non-digital items). The non-scalar columns:

- **`contributors`** — array of structs (author/editor list, attribute group
  798), sorted by `rank`. `affiliationType1`/`affiliation1` carry the full
  `event, message, api` tiering (promoted to the event tier 2026-08-17 by
  framework-owner decision); the `2`/`3` pairs stay `message`/`api` only; the
  rest inherit the parent's full tiering.
- **`webConsumingSystem`** — array of `{wcsName, endDate}` (attribute group
  1121: WEB_CONSUMING_SYSTEM + ECI_RELEASE_DATE), sorted by both fields.
  Was an array of strings until 2026-09-07 (UIFPE-270, owner item 10) — a
  breaking shape change for consumers of the old encoding.
- **`associatedPrograms`** — array of strings (attribute group 1421), sorted
  alphabetically.
- **`marketingCopy`** — array of structs (`contentId`, `description`, `type`,
  `audience`, `geoVisibilityCode`, `owningMarketCode`), sorted by `type`, then
  `audience`, then `geoVisibilityCode` (tie-breakers; entries sharing all three
  still sort unstably — see delta #4 below).
- **`standardComponents`** / **`customComponents`** — arrays of structs from
  the 'Pearson Standard' / 'PEARSON_CUSTOM' BOM structures (added
  2026-08-17, **populated 2026-09-07 — UIFPE-269** once the `bom_*` Silver
  sources landed). Bills are read from the master org, primary structures
  only; each column carries its own derivation block (ADR-0008). Component
  rows carry no product key, so component-only edits land via the pipeline's
  `schedule.recompute` leg on both columns. `standardComponents` sorts by
  `sequenceNumber` (`ITEM_NUM`) then `ppid`; `customComponents` by `ppid`
  then `effectiveDate`.
- **`enablingTechnology`** — array of `{level1, level2}` pairs (groups 881
  legacy / 1407 digital, conditional by catalog side; added 2026-09-07),
  sorted by both fields, duplicates collapsed, all-null pairs dropped.
- **`fulfillmentOrgDetails.marketingInitiative`** — an array of
  `{marketingInitiative, startDate, endDate}` INSIDE the struct (group 1141,
  org-level, several per item-org; added 2026-09-07), sorted by
  (initiative, startDate).
- **`fulfillmentOrgDetails`** — object with 10 org-level fulfillment scalars
  (`sellingRestrictionCode`, `discountCode`, `titleStatusCode`,
  `regionalPublicationDate`, `returnClassCode`, `imprint`,
  `productTaxClassificationCode`, `relevanceValue`, `backOrderIndicator`,
  `defaultSalesOrderSourceTypeCode`) plus the `marketingInitiative` array described above.
  `backOrderIndicator` shares group 1171's non-digital predicate with `titleStatusCode`,
  which costs nothing: group 1171 carries **no** Digital Catalog rows at all
  (measured 2026-09-10, 6.8M rows, zero with `ITEM_CATALOG_GROUP_ID = 10002`).
  Its source carries five spellings for two meanings (`Yes`/`Y` and
  `No`/`NO`/`N`), so the `convertYN` transform normalises it to `Y` or
  `N` (owner, 2026-09-10). Measured: 386,255 -> `Y`, 680,120 -> `N`, and the
  only non-null value reaching the ELSE branch is `N/A`, which the manifest's
  `null_sentinels` already reads as NULL. No source value is dropped. The two newest
  members sit AFTER the array in every artifact — a nested `ADD COLUMN`
  appends, so struct order is load-bearing. On Digital Catalog
  items, `titleStatusCode` and `regionalPublicationDate` are master-level and
  proliferate to orgs by UK/non-UK group (UK = `organizationCode` starting
  `01`, read from the `org_params` org dimension);
  `returnClassCode` and `imprint` are org-level on both sides (imprint is
  conditional by Digital Catalog, returnClass is not).

Every top-level array column declares `array_sort_keys` in the mapping
manifest — required per ADR-3 D11 so channel hashes stay stable across runs.

**Null sentinels (UIFPE-268, 2026-09-07):** the manifest declares `TBD`,
`N/A`, `99998`, `99999` and the runtime renders them as NULL on every Silver
view the SQL reads, so consumers no longer see Oracle's placeholders in any
value column. Two deliberate exceptions: identifier-shaped source columns
(names ending `_ID` / `_NUM`) are never cleaned, because a cleaned key would
hide the row from change detection — so `standardComponents[].sequenceNumber`
(from `ITEM_NUM`) and `categories[].categoryId` can still carry `99999`, and
a sentinel `sequenceNumber` sorts to the end of the array as if it were the
highest real sequence.

**Breaking change accepted inside v1 (owner decision, 2026-09-07).**
`webConsumingSystem` changed from `ARRAY<STRING>` to
`ARRAY<STRUCT<wcsName, endDate>>` on the gold table, both event data schemas
and the REST contract, and every artifact kept its v1 coordinates.
`capabilities/api/guidelines.md` treats a type change as major and would
normally require a `/v2` plus a deprecation window; the owner waived that
because the product entity has no consumers yet — it is still in build phase,
nothing subscribes to the events, and the API's Athena path is unwired. The
waiver is recorded here rather than left implicit. It does not generalise:
the next shape change to this column, once anything consumes it, takes the
versioned path. Note also that the registry compatibility gate is inert
while `APICURIO_REGISTRY_URL` is unset — if it is ever configured, this
artifact would fail its own BACKWARD rule at registration, so the registered
copy must be re-cut from this version rather than evolved from the old one.

**Row domain (UIFPE-271, 2026-09-07):** products only (`SEGMENT1 LIKE 'A%'`)
AND `INVENTORY_ITEM_STATUS_CODE NOT IN ('DRAFT', 'ERROR', 'DELETE',
'RETIRED')`, enforced identically in the SQL WHERE and the manifest's
`sot_filter`. ~2.14M of the previous 6.83M dev rows remain. Identity is not
row domain: `parentProduct` and every component `ppid` are resolved over ALL
products (`items_all`), so they may name an item that has no row in this
table (a RETIRED parent or component). That is deliberate — treat them as
identifiers, not as a foreign key into this table.

## Tier subsets (generated by CI, published to Schema Registry)

| Tier | Schema Registry artifact | Top-level attributes |
|---|---|---|
| event | `product.gold-event-value` | 60 |
| message | `product.gold-message-value` | 60 (identical to event) |
| api | `product.gold-api-value` | 60 (identical to event — there are no api-only attributes) |

(The 3 columns carrying no `x-channels` — `inventoryItemId`, `organizationId`
and `itemCatalogGroupId` — are internal to the Gold table and exposed on no
tier.)

> Recounted 2026-09-20 against `master.json` while adding
> `instructorResourceFiles` (UIFPE-476). The previous figures had drifted by
> more than this one column: they read 54 / 54 / 58 with four attributes named
> as api-only, when all three tiers were already identical and the api-only set
> was already empty. The counts here are computed, not incremented — recompute
> them rather than adjusting by hand. The concentric invariant `event ⊂ message ⊂ api`
is enforced by CI (`scripts/generate_tier_subsets.py`); nested array/object
fields are filtered recursively, and channel hashes are computed over the
projected element so a hidden nested-field change never pings a channel that
doesn't see it.

## How changes flow

1. Business provides/updates the attribute mapping as a spreadsheet; a
   confirmed batch of rows from it drives the edit.
2. One PR updates `master.json` (this schema), `manifest.yaml` +
   `sql/product.sql` (the join recipe), and any Glue code the change needs —
   atomic per ADR-3/ADR-4.
3. `scripts/generate_tier_subsets.py` derives the `event`/`message`/`api`
   subsets from `master.json`'s `x-channels` tags (CI runs this on merge;
   it can also be run locally to preview a subset).
4. `scripts/publish.sh` pushes the master, subsets, and the mapping manifest
   (via `scripts/build_mapping_artifact.py`) to the Pearson Schema Registry.
5. At runtime, new attributes are picked up by the schema-diff auto-DDL in
   the transform (ADR-3 D12): `ALTER TABLE ADD COLUMN` + a one-time full-key
   backfill, `silent` by default (no `_gold_updated_at` movement, no
   change-log rows) unless the manifest requests `emit`.

## Relationship to product.mapping.json

`domains/product/src/schemas/mapping/product/v1/product.mapping.json` (Raj's, refreshed
2026-07-31 from the Excel, 55 columns incl. the dotted
`fulfillmentOrgDetails.*` fields and `joinGrain`) is the **authored intake** —
the human-maintained business mapping. This `master.json` plus
`../../../mapping/product/v1/manifest.yaml` and its `sql/product.sql` are the
**compiled runtime artifacts** the Glue pipeline actually consumes. The two
are not yet fully reconciled; the remaining deltas are:

1. ~~The mapping has `organizationid` in lowercase, whereas the deployed PK
   column is camelCase `organizationId`~~ — **RESOLVED**: `goldColumnName`
   was corrected to camelCase `organizationId` in `product.mapping.json` and
   in the source spreadsheet (`product-gold-attribute-mapping-template.xlsx`,
   Scalar sheet, cell A5) (2026-08-01).
2. ~~`master.json` does not yet carry `fulfillmentOrgDetails.returnClass` or
   `fulfillmentOrgDetails.imprint`~~ — **RESOLVED**: both fields were added to
   `fulfillmentOrgDetails` (struct), `manifest.yaml` `canonical_lineage` +
   `column_types`, and `sql/product.sql` (2026-08-01).
3. Whether the mapping's dotted `fulfillmentOrgDetails.*` columns should be
   represented as dotted columns or as a struct is still to be settled by
   ADR — resolving delta #2 kept the compiled artifact's existing struct
   representation; the mapping still uses dotted names. **This is the only
   remaining open delta.**
4. ~~`marketingCopy`'s sort key: the intake (mapping.json nested sheet)
   flags `type` as the sort key, but the compiled runtime
   (`manifest.yaml` `array_sort_keys` + `sql/product.sql`) sorted by
   `contentId`~~ — **RESOLVED**: the runtime now sorts by
   `[type, audience, geoVisibility]` (2026-08-01), matching the intake's
   primary key with two additional tie-breakers (mirroring the `contributors`
   sort pattern). Residual risk: entries sharing all three keys still sort
   unstably — no further tie-breaker (e.g. `contentId`) is implemented; see
   the comment above `array_sort_keys.marketingCopy` in `manifest.yaml`.

## Breaking-change policy

- Adding an optional property → minor version (`v1` stays).
- Removing or renaming a property, or changing required types → new major
  version (`v2`).
- Re-tiering a property (e.g. moving from `api` to `event`) → minor version.
  Consumers in the smaller tier are unaffected; consumers in the larger tier
  always saw the property.
